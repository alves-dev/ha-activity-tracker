# Context Mesh Framework

## Overview

Context Mesh keeps durable project context separate from implementation. Its working loop is **Intent → Build → Learn**:

1. **Intent** records the user or business outcome before work begins.
2. **Build** implements an approved approach while following decisions and patterns.
3. **Learn** records outcomes, changes in understanding, and significant discoveries.

## File Type Separation

| File type | Purpose | Must contain | Must not contain |
| --- | --- | --- | --- |
| `intent/project-intent.md` | Project purpose and current scope | What the project is, why it exists, current features | Technical architecture or code examples |
| `intent/feature-*.md` | Product capability | What users can do, value, functional acceptance criteria | Libraries, file paths, algorithms, or code |
| `decisions/*.md` | Architecture decision record (ADR) | Technical choice, rationale, alternatives, outcomes | Step-by-step code recipes |
| `knowledge/patterns/*.md` | Reusable implementation guidance | How to implement, conventions, code examples, participating files | Product requirements as the primary content |
| `knowledge/anti-patterns/*.md` | Practices to avoid | Risk, symptoms, preferred alternative | Unrelated feature scope |
| `agents/*.md` | Focused agent operating instructions | Role, inputs, outputs, constraints | General product intent duplicated from intent files |
| `evolution/*.md` | Change and learning history | Dated changes, outcomes, insights | Undated design proposals |

Features may link to decisions and patterns, but remain high-level. Decisions link back to the intent they serve. Patterns link to the decisions and features they implement.

## Plan, Approve, Execute (Mandatory)

Before a material change:

1. **Plan:** identify the affected feature intent, decisions, patterns, risks, and validation.
2. **Approve:** obtain explicit user or project authorization for the proposed scope when approval is required by the workflow.
3. **Execute:** implement only the approved plan, validate it, and update Context Mesh in the same change.

For small, clearly authorized maintenance work, the request itself can serve as approval; the plan still needs to be traceable in the relevant context and change record. Do not silently substitute a new technical approach for a documented decision.

## When to Create Files

Create or update a feature file when user-visible behavior, scope, or acceptance criteria change. Create an ADR before adopting a durable technical choice, framework, storage model, external dependency, or architectural approach. Create a pattern when code demonstrates a reusable convention or example future work should follow. Create an anti-pattern when a recurring harmful approach is observed. Add a learning file for a significant discovery whose value exceeds a changelog entry.

Do not create a new file for trivial refactors, formatting-only changes, duplicated decisions, temporary debugging notes, or facts already covered by the appropriate existing context file. Update the existing file instead.

## Context Structure

```text
context/
├── .context-mesh-framework.md
├── intent/                 # What and why
├── decisions/              # Technical choices and rationale
├── knowledge/
│   ├── patterns/           # Reusable implementation guidance
│   └── anti-patterns/      # Practices to avoid
├── agents/                 # Optional focused agent instructions
└── evolution/              # Changelog and learned outcomes
```

## Bidirectional Links

- Each feature links to the decisions that implement it and relevant patterns.
- Each decision links back to its project intent and affected features; link related decisions where useful.
- Each pattern links to the decision it supports and the features where it is used.
- Use repository-relative Markdown links and keep link labels descriptive.
- When adding a relationship, update both ends when the relationship is material.

## Status Requirements

Every intent, decision, and pattern file includes a `## Status` section with at least a creation date and current status. Intent files state the phase; decisions state whether they are proposed, accepted, superseded, or deprecated; patterns state whether they are active or retired. Existing-code documentation must say when rationale or alternatives are inferred rather than documented.

## Definition of Done

For a completed build change:

- [ ] Affected feature intent is current.
- [ ] Required ADR exists and is accepted before implementation.
- [ ] Code follows applicable patterns and avoids documented anti-patterns.
- [ ] Relevant tests and validation pass.
- [ ] Decision outcomes are updated if the result differs from the planned approach.
- [ ] Changelog records the user-relevant or context-relevant change.
- [ ] Bidirectional links are accurate.
